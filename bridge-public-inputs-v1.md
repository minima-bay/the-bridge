# Bridge proof public inputs v1

Date: 2026-08-18  
Status: canonical release and payout research subset, no deployed verifier; cancellation extension required

## 1. Purpose

This schema binds an Ethereum light-client proof to one exact client transition and one exact
Ethereum-to-Minima action. It is fixed-width, integer-only and destination-specific. It is not
evidence until a proof is generated by the pinned program and verified inside Minima consensus.

The reverse Minima-to-Ethereum proof needs a separate schema for Minima cumulative-work, cascade,
MMR and redemption facts. It must not overload Ethereum-specific fields in this schema.

This v1 subset is not a complete bridge schema. It still models deposits as permanently locked and
supports only the `EMPTY` to `RELEASED` nullifier transition. `P1` and `P2` remain open until a
distinct cancellation action proves the exact finalized `PENDING` vault record and its committed
Minima authority, binds the authority signature to the complete cancellation domain, defines
`EMPTY` to `CANCELLED`, and lets the Ethereum vault prove-gate `PENDING` to `REFUNDED` while restoring
reserved inbound capacity exactly once. Existing 1005-byte fixtures do not evidence that extension.

## 2. Canonical encoding

`publicValuesV1` is the byte concatenation of the fields below in table order.

- Integers are unsigned, big-endian and exactly the stated width.
- Byte arrays are exactly the stated width and have no length prefix.
- Addresses use raw bytes, not text or checksum formatting.
- No field may be omitted, shortened or encoded as JSON for proof verification.
- Reserved enum values fail closed.
- `publicValuesHash = SHA2-256(publicValuesV1)`.
- Domain string bytes are ASCII and exactly `MINIMA_ETH_USDT_BRIDGE_V1` padded on the right with zero
  bytes to 32.

## 4. Exact action rules

Every action authenticates the finalized Ethereum execution-header timestamp and proves
`executionTimestampMillis = header.timestamp * 1000` within unsigned 64-bit range. The covenant uses
guarded differences only:

```text
if executionTimestampMillis > @BLOCKMILLI:
    executionTimestampMillis - @BLOCKMILLI <= maxEthereumFutureSkewMillis
else:
    @BLOCKMILLI - executionTimestampMillis <= maxEthereumHeadAgeMillis
```

Both limits are fixed configuration bindings. The branch subtracts the smaller unsigned value from
the larger one, so it needs no division, multiplication or overflow-prone addition in KISS. This
source-age rule applies even when the finalized slot advances, so a relayer cannot reset freshness by
feeding old heads one at a time. Minima block timestamp manipulation and the selected bounds remain
explicit production risks and test gates.

### 4.1 Action 1: client update only

```text
direction = 1
action = 1
newFinalizedSlot > priorFinalizedSlot
newEthereumClientStateHash != priorEthereumClientStateHash
newClientAcceptedMinimaBlock is within the fixed posting lag of current @BLOCK
messageId = 0
sourceRecordId = 0
newPayoutRecordId = priorPayoutRecordId
newCumulativePayoutAtoms = priorCumulativePayoutAtoms
sourceAmountAtoms = 0
destinationAmountAtoms = 0
recipientType = 0
recipientAddressData = 0
newIssuedLiability = priorIssuedLiability
newPendingRedemption = priorPendingRedemption
newIssuedLiability + newPendingRedemption <= attributableVaultBalance * decimalScale
newBridgeStateHash != priorBridgeStateHash
```

`decimalScale` remains the configured value. The proof updates the Ethereum consensus and execution
state only. The bridge hash changes because it commits the new Ethereum-client hash and current
vault balance, while liability, pending redemption, reserve, nullifier and fixed-supply fields remain
unchanged. The proof also establishes that the vault's current payout counter equals
`priorPayoutRecordId`, so an unacknowledged payout cannot be skipped by action 1. It cannot release
reserve tokens.

### 4.2 Action 2: inbound release

```text
direction = 1
action = 2
newFinalizedSlot >= priorFinalizedSlot
newEthereumClientStateHash = priorEthereumClientStateHash when the finalized slot is reused
newEthereumClientStateHash != priorEthereumClientStateHash when the finalized slot advances
newClientAcceptedMinimaBlock = priorClientAcceptedMinimaBlock when the slot is reused
current @BLOCK - priorClientAcceptedMinimaBlock <= maxClientReuseBlocks when the slot is reused
newClientAcceptedMinimaBlock is within the fixed posting lag of current @BLOCK when the slot advances
sourceAmountAtoms > 0
destinationAmountAtoms = sourceAmountAtoms * decimalScale
recipientType = 1
recipientAddressData != 0
newIssuedLiability = priorIssuedLiability + destinationAmountAtoms
newPendingRedemption = priorPendingRedemption
newPayoutRecordId = priorPayoutRecordId
newCumulativePayoutAtoms = priorCumulativePayoutAtoms
newIssuedLiability + newPendingRedemption <= attributableVaultBalance * decimalScale
newBridgeStateHash != priorBridgeStateHash
messageId != 0
```

If `newFinalizedSlot > priorFinalizedSlot`, the proof performs an authenticated Ethereum client
update and the deposit proof together. If the slots are equal, the proved program must show that the
beacon root, execution block, state root, receipts root, committees and fork state exactly equal the
already authenticated prior state.

Deposit eligibility comes from the persistent vault record under the authenticated current
`executionStateRoot`, not from retaining the event block's receipts root. A later finalized state can
still prove every unconsumed immutable deposit record. Advancing the light client therefore cannot
skip or strand an earlier deposit, and multiple records from the same block remain independently
claimable.

`attributableVaultBalance` must come from authenticated finalized Ethereum state under the exact
vault and token code semantics. It is not supplied by an RPC or monitor.

The proof also establishes that the current vault payout counter equals `priorPayoutRecordId`.
Pending payouts must be acknowledged by action 3 before action 2 can advance across them.

The covenant enforces the acceptance-block rules using Minima's consensus `@BLOCK` value. An
equal-head proof expires after `maxClientReuseBlocks`; it cannot be refreshed without a strictly newer
authenticated Ethereum finalized slot. This bounds stale-state exposure but does not remove USDT
issuer risk inside the accepted window.

`pendingRedemption` prevents both directions from relying on the same collateral. A Minima return
decreases issued liability and increases pending redemption by the same amount. Only a proof of the
finalized Ethereum payout decreases pending redemption, and that proof also authenticates the lower
vault balance. Every inbound release therefore reserves backing for all accepted but not yet
acknowledged redemptions.

For a fresh six-decimal Minima token, `decimalScale = 1`. If an eight-decimal Minima token is ever
selected, `decimalScale = 100`. Reverse transfers must reject amounts not divisible by 100. The token
choice remains an open founder decision and is not inferred here.

### 4.3 Action 3: finalized payout acknowledgement

```text
direction = 1
action = 3
newFinalizedSlot >= priorFinalizedSlot
newClientAcceptedMinimaBlock = priorClientAcceptedMinimaBlock when the slot is reused
current @BLOCK - priorClientAcceptedMinimaBlock <= maxClientReuseBlocks when the slot is reused
newClientAcceptedMinimaBlock is within the fixed posting lag of current @BLOCK when the slot advances
sourceAmountAtoms > 0
destinationAmountAtoms = sourceAmountAtoms * decimalScale
newPayoutRecordId > priorPayoutRecordId
sourceRecordId = newPayoutRecordId
newCumulativePayoutAtoms > priorCumulativePayoutAtoms
sourceAmountAtoms = newCumulativePayoutAtoms - priorCumulativePayoutAtoms
recipientType = 0
recipientAddressData = 0
newIssuedLiability = priorIssuedLiability
newPendingRedemption = priorPendingRedemption - destinationAmountAtoms
newIssuedLiability + newPendingRedemption <= attributableVaultBalance * decimalScale
newBridgeStateHash != priorBridgeStateHash
messageId != 0
```

The proof authenticates one cumulative append-only payout range, not one payout. The vault assigns
sequential payout record IDs and stores cumulative paid atoms at every record. The proved delta from
`priorPayoutRecordId` to `newPayoutRecordId` acknowledges every record in that range atomically. This
allows all payouts reflected in one end-of-block balance to be acknowledged in one Minima transition.
The same equal-slot and advancing-slot rules apply to `newEthereumClientStateHash` as in action 2.

## 5. Recipient encoding

`recipientType = 1` means `recipientAddressData` is exactly the 32 raw address bytes used by a Minima
transaction output and exposed by Minima's internal address data. The Ethereum vault accepts a
`bytes32`, not an `Mx` string, and rejects all-zero data. User interfaces may decode an `Mx` address
with the network's canonical Minima address codec, but the decoded 32 bytes are the only committed
value. No case folding, text normalization, checksum text or alternate-length encoding enters the
proof.

The Minima covenant requires output 2's raw address data to equal `recipientAddressData` byte for
byte. `destinationNetworkId` prevents the same raw value from authorizing a different configured
Minima network.

## 6. Message identifier

The Ethereum vault stores a bridge-specific commitment in persistent contract state. A direct USDT
`Transfer` or historical event alone is not sufficient.

```text
messageId = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_ETH_USDT_BRIDGE_V1") ||
  UINT8(1) || UINT8(2) ||
  UINT256_BE(sourceChainId) || sourceGenesisRoot || bridgeDeploymentId ||
  vaultAddress || tokenAddress || UINT64_BE(sourceRecordId) ||
  UINT128_BE(sourceAmountAtoms) || UINT8(1) || recipientAddressData ||
  UINT64_BE(configurationEpoch)
)
```

The vault assigns a unique deposit record ID, accepts the raw 32-byte recipient, checks the configured
decimal scale and enforces its fixed-supply capacity before taking funds. The proof establishes that
the exact record exists under the current finalized state root, is non-refundable and was not
previously consumed by the destination state.

Version 1 requires immutable vault runtime and no proxy or upgrade administrator. `vaultCodeHash` is
the EVM `EXTCODEHASH` of that runtime. A governed or proxy vault is a different trust model and needs
a new schema, configuration epoch and founder decision. USDT issuer controls remain an external risk.
The accepted reuse-window value and the response to a token-code or balance-semantics change remain
production gates.

For every action-3 proof, `messageId` is the canonical payout batch ID. Individual redemption IDs
remain inside the persistent vault payout records:

```text
messageId = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_PAYOUT_BATCH_V1") ||
  priorEthereumClientStateHash || newEthereumClientStateHash ||
  priorBridgeStateHash || newBridgeStateHash ||
  UINT64_BE(priorPayoutRecordId) || UINT64_BE(newPayoutRecordId) ||
  UINT128_BE(priorCumulativePayoutAtoms) || UINT128_BE(newCumulativePayoutAtoms) ||
  UINT64_BE(configurationEpoch)
)
```

## 7. Persistent vault record encodings

The pinned vault runtime maintains two append-only mappings. Record IDs are unique and never reused.
Records cannot be deleted or changed to refundable states.

```text
depositRecordHash = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_VAULT_DEPOSIT_V1") ||
  UINT64_BE(sourceRecordId) || messageId || UINT128_BE(sourceAmountAtoms) ||
  UINT8(1) || recipientAddressData || UINT64_BE(configurationEpoch) || UINT8(1)
)

payoutRecordHash = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_VAULT_PAYOUT_V1") ||
  UINT64_BE(sourceRecordId) || redemptionId || UINT128_BE(sourceAmountAtoms) ||
  ethereumRecipient20 || UINT128_BE(cumulativePayoutAtoms) ||
  UINT64_BE(configurationEpoch) || UINT8(1)
)
```

Final status byte `1` means permanently locked for a deposit and permanently paid for a payout. The
proof program verifies the exact vault code and storage layout, then proves the mapping value under
the current finalized `executionStateRoot`. Events may be used for discovery and audit, but never as
the only continuing authorization record.

The vault enforces `sourceRecordId = previousPayoutRecordId + 1` and
`cumulativePayoutAtoms = previousCumulativePayoutAtoms + sourceAmountAtoms` for every payout. Action 3
may acknowledge any later prefix, subject to the proof-system's fixed maximum batch work.

## 10. Ethereum bootstrap requirements

Ethereum light-client bootstrap requires out-of-band genesis data, a fork schedule and a trusted
recent finalized checkpoint within weak subjectivity. Bootstrap authority, maximum checkpoint age,
offline recovery and fork-schedule upgrades are explicit governance inputs. A bootstrap or refresh
must never reset message consumption, liability, pending redemption or reserve state.

## 11. Replay rules

- Each accepted `messageId` is consumed exactly once in consensus.
- Version 1 uses a sparse deposit-nullifier root in the canonical bridge state. The proof program
  proves non-membership of `messageId` under the prior root and insertion under the new root.
- `sourceRecordId` identifies a vault record but does not impose in-order Minima execution.
- The exact sparse-tree construction is in section 12.
- Proofs cannot cross direction, chain, deployment, verifier version, program, key or epoch.
- Same-message concurrent submissions race for the one canonical state coin. Losers rebuild from the
  mined state and then fail as already consumed.

## 12. Canonical tagged nullifier tree

The tree is a depth-256 binary sparse Merkle tree using SHA2-256.

```text
key = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_NULLIFIER_KEY_V1") ||
  UINT8(1) || messageId
)

leaf = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_NULLIFIER_LEAF_V1") ||
  key || UINT8(status)
)

node[level] = SHA2-256(
  ASCII_ZERO_PAD_32("MINIMA_NULLIFIER_NODE_V1") ||
  UINT16_BE(level) || leftChild || rightChild
)
```

The path uses key bits most-significant-bit first. `level = 0` combines leaves and `level = 255`
produces the root. The empty leaf is `SHA2-256(ASCII_ZERO_PAD_32("MINIMA_NULLIFIER_EMPTY_V1"))`.
Empty roots are derived recursively with the node formula and equal left and right children.

Status:

```text
0 = empty, represented only by the canonical empty leaf
1 = deposit released
```

The only transition is empty to deposit released. No transition deletes a leaf or returns it to
empty. Outbound returns rely on the spent returned coin ID and Ethereum's consumed redemption map,
not a Minima sparse-tree update. The proved program checks the full prior deposit path and exact
successor root. The covenant binds that root to state port 10.

## 13. What this schema does not prove

The JSON fixture and validator in this directory prove only deterministic public-value encoding and
local invariant checks. They do not prove client-state or reserve-state hash implementations,
Ethereum finality, receipt inclusion, vault solvency, ZK proof validity, Minima covenant validity or
mineability. Dedicated state-hash and sparse-tree fixtures remain required before Core or covenant
implementation.

## 14. Source anchor for Minima address data

Current Minima `Address` source distinguishes raw `mAddressData` from the checksum Base32 Minima
address and exposes `convertMinimaAddress` to recover the raw data. Version 1 deliberately accepts
only 32-byte raw address data even though the generic codec can carry other lengths:
[Address.java](https://github.com/minima-global/Minima/blob/master/src/org/minima/objects/Address.java).
